# 项目复盘与独立开发手册

> 这套文档为"下一次同类需求能独立完成"而写。它不是项目介绍，而是一条**从需求到交付的完整思考路径**：每一篇都包含"可复用的方法 + 本项目的真实做法 + 你可以照着做的步骤"。
>
> 建议先读本篇，再按顺序读 01–05。

## 1. 项目一页纸

| 项 | 内容 |
|---|---|
| 项目名 | 实验对话系统（Experiment Chat） |
| 一句话 | 面向行为实验的"对话式问卷"平台：被试在手机上像聊天一样完成材料阅读、量表、创作、AI 反馈、再创作；研究者在管理端编排题目、预览、看数据、导出 Excel |
| 研究背景 | 2 组被试间实验：AI 负面反馈 × 目标清晰度（高/低）；因变量为第二次广告语创造力、反馈公平性、元过程、任务过程 |
| 核心用户 | 研究者/实验助理（管理端）、被试（手机端）、系统（服务端状态机） |
| 关键约束 | 现场可能无外网；目标电脑不装环境；计时必须可信；两组材料只能差操纵；数据要直接进统计 |
| 技术栈 | Node.js ≥ 22.13（`node:http` + `node:sqlite`）、原生 HTML/CSS/JS、无构建、零第三方依赖 |
| 数据 | 单文件 SQLite（WAL）：模板、问卷、会话快照、消息、作答、设置、账号 |
| 交付 | 局域网预实验便携包（内置 node.exe、双击启动、二维码）+ 公网上线包（一键更新） |
| 质量 | 平台行为自检 + 内容一致性自检 + 无头浏览器走查 + 并发探针 + 模拟被试 |
| 规模 | `server.js` ~2475 行、`db.js` ~1567 行、`admin.js` ~4358 行、`chat.js` ~2162 行；23 个 commit（2026-09-26 至 10-17） |

**一句话简历版**：

> 独立设计并实现面向行为实验的对话式问卷平台（Node.js + SQLite + 原生前端），以"一切皆题目"统一模型支撑 10 种题型与服务端权威计时门控；通过会话快照、幂等提交、断点恢复保障数据一致性；交付零依赖便携包与一键上线流程，支撑两组预实验收数据。

## 4. 怎么读才有效

每篇都用同一个结构：

```text
【方法】可复用的思考方式
【本项目】真实做法与代码位置
【代价/边界】这么做的代价，什么时候该换
【练习】动手验证
```

建议：

1. **不要背结论**，要能复述"约束 → 选择 → 代价"。
2. **每读一个设计，问三个问题**：解决什么问题？不这么做会怎样？什么条件下会改？
3. **边读边打开代码**：文档里的函数名/行号是路标，不是替代品。
4. **每篇末尾的练习至少做一题**，否则只是"看懂了"，不是"会做"。
5. **用自己的话写一页总结**，发给自己/团队；能讲清楚才算掌握。

## 6. 作品集/简历写法

### 6.1 STAR 版本

**S（情境）**：研究需要两组被试完成"创作 → 负面反馈 → 再创作"的在线实验，原流程靠 QQ 群人工发材料、计时、记录，存在时间不一致、数据错漏、现场无外网等问题。

**T（任务）**：独立做一个能在实验室离线运行、手机扫码即用、计时可信、数据可直接分析的实验平台。

**A（行动）**：

- 把实验程序表翻译成"被试时间线 + 变量表"，抽象出"一切皆题目"的统一模型（10 种题型 + 题目级参数）；
- 设计服务端权威的状态机：呈现时刻、强制等待、最短/最长作答、共用窗口、清屏点、幂等提交、会话快照；
- 用 Node 内置 `http` + `node:sqlite` + 原生前端实现，零第三方依赖；单文件 SQLite + WAL；
- 建立平台层/内容层双层自检、无头浏览器走查、并发探针；用"改时间戳"把自检从 6m47s 降到 0.7s；
- 交付局域网便携包（内置 node、双击启动、二维码）与公网一键更新包。

**R（结果）**：

- 支撑两组预实验按统一流程收数据；一位被试全程约 27–31 次请求，读题/打字/倒计时期间零请求；
- 本机探针：单请求平均 ~2.3ms / p95 ~6ms；300 并发提交 310–758ms（约 396–968 QPS，视版本/测试方式）；
- 自检 70+ 断言；内容差异（两组只差操纵）可自动校验；
- 现场无需安装 Node，双击即可启动。

> 数字要写清测试条件（本机、单进程、开发机），不要包装成生产压测。

### 6.2 三条简历 bullet（可直接改）

1. 独立设计并实现对话式实验平台（Node.js/SQLite/原生前端），以"一切皆题目"统一模型支撑 10 种题型、题目级计时门控与会话快照，保障多组实验内容隔离与数据可复现。
2. 设计服务端权威的作答状态机（强制等待/最短提交/最长作答/共用窗口/清屏/幂等/断点恢复），将计时与数据校验从不可信前端收敛到服务端，支撑数百人并发下的数据一致性。
3. 建立双层自检 + 无头浏览器走查 + 并发探针，自检耗时从 6m47s 降至 0.7s；交付零依赖便携包与一键上线流程，实现实验室离线部署。

### 6.3 面试可能追问

| 问题 | 回答要点 |
|---|---|
| 为什么不用 React/Express？ | 约束驱动：离线、零安装、单进程、无构建；代价是管理端文件大、路由手写；团队/复杂度上来会换 |
| 为什么 SQLite 能扛几百人？ | 请求模型是逐题提交、无轮询（每人约 30 次请求）；WAL + `synchronous=NORMAL`；本机探针数据；单写者是多实例时的上限 |
| 计时为什么必须服务端？ | 前端可改时间/刷新/切后台；服务端记录 `presented_at` 并在提交时校验；提前提交 400 |
| 怎么保证改问卷不影响进行中会话？ | 会话创建时 `items_json` 快照；`parseSession` 只读快照 |
| 重复提交怎么处理？ | `itemId` 必须等于当前作答单元，否则幂等忽略，防串题 |
| 清屏为什么记服务端？ | 否则刷新会把清空前的消息重新下发；`sessions.clear_seq` 过滤 |
| 两组差异怎么保证？ | `sync-group-content.js` 按种子重建 + 逐字段比对；`consistency-check.js` 断言 |
| 自检为什么能这么快？ | 直连数据库回拨 `presented_at`，不真实等待门控；跑的是真实门控值 |
| 最大的技术债？ | 单体 `server.js`/`admin.js`、item JSON 无 schema、手写迁移、单机 SQLite；给出触发条件与迁移路径 |
| 如果重做？ | 保留统一模型/服务端权威/快照/零依赖交付；拆模块、加 schema 校验、版本化迁移、管理端上框架、Playwright + CI |

### 6.4 不要写进简历的内容

- "支撑万人并发"——没有生产证据；
- "AI 智能反馈"——实际是预设文案，避免误导；
- "零 bug/完美"——不真实；
- 被试数据、学校/导师联系方式、未公开的研究假设（除非获得许可）。

## 7. 这套文档没覆盖的部分（下一阶段）

这次只完成"需求 → 选型 → 框架 → 搭骨架 → Git"。后续可以按同样方式补：

1. **核心功能实现**：10 种题型、题组、参数系统、清屏、重做、恢复；

3. **质量体系**：平台/内容双层自检、截图走查、并发探针、模拟数据；
4. **部署与运维**：便携包、上线包、Windows 计划任务、Nginx、备份/回滚；
5. **研究数据**：导出字段、清洗、统计分析、预实验复盘；
6. **作品集**：README、架构图、演示 GIF、Release notes。

每一阶段都可以沿用本套文档的结构：**方法 → 本项目 → 代价 → 练习**。

## 8. 最后三句话

1. **需求阶段的目标不是"写全"，而是"把不确定变成决定"**——每个决定都留下理由和代价。
2. **架构的核心不是分层，而是"谁说了算"**——这个项目里，时间、答案、清屏、进度都由服务端说了算。
3. **能独立完成的标准不是"记得怎么写"，而是"换一个需求，还能按同样的方法推一遍"**。
