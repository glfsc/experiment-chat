## 2. 分层职责

| 文件 | 职责 | 不该放什么 |
|---|---|---|
| `server.js` | HTTP 路由、静态资源、鉴权、状态机、预览、导出编排、限流、安全头 | 复杂 SQL（放 `db.js`）；实验文案（放 `seed-content.js`） |
| `db.js` | 建表/迁移、种子、全部 SQL、题目归一化、富文本排版（`body16/materialHtml`） |  HTTP 细节、页面渲染 |
| `seed-content.js` | 实验材料文案常量（任务信息、两版任务要求、反馈、思考稿、量表题） | 业务逻辑 |
| `xlsx.js` | 纯函数：二维数据 → xlsx 二进制 | 数据库查询 |
| `public/assets/richtext.js` | 富文本清洗/转换，浏览器与 Node 共用 | DOM 依赖（要能在 Node 跑） |
| `public/admin.html` + `admin.js` | 管理端 SPA（hash 路由、编辑器、预览、数据页） | 直接写库 |
| `public/chat.html` + `chat.js` | 被试端 SPA（消息流、题卡、门控倒计时、恢复） | 计算门控的权威时间 |
| `scripts/` | 启动器、打包、自检、探针、模拟数据、内容同步 | 运行时依赖 |
| `design/` | 设计稿与重构方案 | 生产代码 |

**注意：这不是严格的分层架构。** `server.js` 同时承担 HTTP 层、应用服务层和部分领域逻辑。对单人项目这是有意的取舍：减少文件跳转，代价是大文件。第 12 节会讲什么时候该拆。

## 4. 被试端请求生命周期

### 4.1 首次进入

```text
手机扫码 /chat?q=uegnugph
  │
  ├─ GET /chat.html（静态）
  ├─ GET /api/bootstrap?q=uegnugph
  │     ├─ 问卷不存在 → 404
  │     ├─ 没有 session → 返回 questionnaireTitle / assistant 配置 / session:null
  │     └─ 有 session → 校验是否跨问卷、是否超恢复窗口、是否该作废
  │
  ├─ 前端发现 session:null → POST /api/session { q }
  │     ├─ 取问卷 items
  │     ├─ nextSessionSeq(q) 分配 seq
  │     ├─ createSession({ items })  ← 题目快照
  │     ├─ emitMessagesBetween(session, plan, 0, now) ← 发出首个单元前的消息
  │     ├─ applyRefreshPoint(...) ← 如果首题是清屏点
  │     └─ 返回 sessionPayload（messages/replay/action/nowMs/totals）
  │
  └─ 前端渲染：消息逐条播 → 当前题卡 → 倒计时
```

### 4.2 一次作答提交

```text
被试点「确认提交」
  │
  ├─ POST /api/step {
  │     sessionId, itemId, value/values/text/order/consent/ack, elapsedMs
  │   }
  │
  ├─ applyStep(st, sessionId, body)
  │   1. 会话存在且 in_progress？
  │   2. body.redo === true？ → 走 applyRedoStep（只改已答打分题）
  │   3. 解析 plan（parseSession，带缓存）
  │   4. completedCount = 已答作答单元数
  │   5. 当前单元 = plan.units[completedCount]
  │   6. itemId 必须等于当前题 → 否则幂等忽略（防"答完一题跳过两题"）
  │   7. computeAction 算门控：
  │        now < availableAt  → 400 too_early
  │        now < minSubmitAt  → 400 too_early
  │   8. validateAnswer 校验答案（题型规则、文本断言、题组子题）
  │   9. 写 responses（题组写多行）
  │  10. 写用户回显消息 messages(role=user)
  │  11. emitMessagesBetween(nextCount) 发出下一单元之前的消息
  │  12. 如果下一题是清屏点 → 记 clear_seq，返回 clearStream
  │  13. 还有单元？ → 计算 nextAction；没有了 → finishSession
  │
  └─ 返回 {
       userMessage, messages, clearStream, action, nowMs,
       session, answeredCount, totalAnswers, totalQuestions, currentQno
     }
```

### 4.3 刷新/恢复

```text
GET /api/bootstrap?q=...&session=<id>
  ├─ 会话跨问卷？ → 忽略
  ├─ 超过自动作废时长？ → status=abandoned，释放设备
  ├─ 超过恢复窗口？ → 当作新会话
  ├─ 进行中 → touchSession（算一次活动）
  └─ 返回 sessionPayload：
       messages = 当前可见消息（按 clear_seq 截断）
       replay   = 重建已答卡片（历史）
       action   = 当前待作答单元（含门控时间）
```

`buildReplay` 的作用：刷新后把"已经答过的题卡"重新渲染成只读/可折叠状态，而不是让被试从零开始。

### 4.4 管理端请求

```text
POST /api/auth/login → token
GET  /api/admin/meta → 题型/参数/默认题目
GET  /api/admin/experiments / questionnaires → 列表
GET  /api/admin/questionnaire?id=... → 单份（含 items）
POST /api/admin/questionnaire/update → 保存（items 整组 JSON）
POST /api/admin/preview → 创建内存预览会话
GET  /chat?preview=<id> → 真 iframe 加载被试端
POST /api/preview/step / seek / speed → 预览推进/跳题/倍速（不落库）
GET  /api/admin/questionnaire/sessions → 会话列表
GET  /api/admin/questionnaire/session?id=... → 个案（对话 + 作答）
GET  /api/admin/questionnaire/export.xlsx?id=... → 导出
```

## 5. 状态机详解

### 5.1 三个核心函数

| 函数 | 位置 | 作用 |
|---|---|---|
| `parseSession(session)` | `server.js:150` | 把 `sessions.items_json` 解析成 `{ items, units }`；`units` 只含非消息题，并给需要作答的题编 `qno` |
| `computeAction(session, plan, completedCount, now)` | `server.js:238` | 计算当前单元的题面、门控时间戳、共用窗口标记，返回给前端 |
| `applyStep(st, sessionId, body)` | `server.js:689` | 校验 + 落库 + 发消息 + 推进；真实会话与预览会话共用 |

### 5.2 `parseSession` 的计划缓存

```js
const planCache = new Map(); // sessionId -> { items, units, pendingAt, itemsJson }
```

- 作答热路径不重复解析几 KB 的 `items_json`；
- 缓存键包含 `pending_presented_at` 与 `items_json`，会话一旦变化就失效；
- 上限 2000 条，超出淘汰最早一条（简单 FIFO，够用）。

> 【方法】缓存不是越多越好。这里的缓存只省"解析 JSON"这一件小事，但每次提交都会走，收益稳定；缓存失效条件必须包含"数据变了"。

### 5.3 消息发出：`emitMessagesBetween`

从"上一单元的下标"到"当前单元的下标"之间，把所有 `message` 题按顺序落库并返回：

```js
function emitMessagesBetween(session, plan, afterAnswerIndex, nowMs, st) {
  const fromItem = afterAnswerIndex > 0 ? units[afterAnswerIndex - 1].index : -1;
  const toItem = afterAnswerIndex < units.length ? units[afterAnswerIndex].index : plan.items.length;
  // 遍历 (fromItem, toItem) 之间的 item：
  //   只处理 type === 'message' 且 text 非空
  //   遇到 refresh 参数 → 记 clear_seq，本批只返回清屏点之后的消息
  //   把 thinking/thinkMs/typeMs 一并落库
  //   返回 { messages, cleared }
}
```

关键设计：

- **消息不是定时任务**：没有后台队列，消息在被试提交后的同一次请求里发出；
- **清屏点可挂在消息上**：遇到清屏点，之前的消息不下发（但仍在库里）；
- **节奏随消息落库**：刷新后回放用的是同一份 `thinking/thinkMs/typeMs`，不会"第二次播放变快/变慢"。

### 5.4 门控计算：`computeAction`

```js
const wait = effLimit(item, 'wait');
const minSubmit = effLimit(item, 'minSubmit');
const maxAnswer = effLimit(item, 'maxAnswer');

if (minSubmit > 0 || maxAnswer > 0) {
  const win = windowStartFor(...);           // 共用窗口起点
  minSubmitAtMs = win.startMs + minSubmit*1000;
  deadlineMs = win.startMs + maxAnswer*1000;
}

return {
  ...base,
  availableAtMs: wait > 0 ? presentedMs + wait*1000 : 0,
  minSubmitAtMs, deadlineMs,
  sharedWindow,
  nowMs, timeScale,
  waitSec, minSubmitSec, maxAnswerSec,
  ...itemDescriptor(item)   // 题面/选项/子题（不含正确答案）
};
```

**注意 `itemDescriptor` 不下发正确答案**：单选/多选的 `correct` 只在服务端用于导出对错。

### 5.5 幂等：为什么必须校验 `itemId`

```js
const bodyItemId = String(body.itemId || '').trim();
if (bodyItemId && bodyItemId !== item.id) {
  return { status: 200, payload: { ...sessionPayload(session, st), ignored: true } };
}
```

没有这段，会出现：

- 前端自动提交的请求迟到，被记到下一题；
- 用户双击提交，第二次把下一题答了；
- 旧页面缓存的请求，串到新会话。

**幂等不是"重复请求返回一样的结果"这么简单，而是"重复请求不能产生新的副作用"。**

### 5.6 重做：独立通道

打分题重做走 `applyRedoStep`：

- 只允许已提交的 `rating`；
- 只允许题目参数 `redo=1`；
- 就地更新 `responses` 那一行（`redoResponse`），不写新行、不推进进度；
- 同步更新用户回显消息；
- 刷新后不再提供重做（前端根据 `redo` 参数与已答状态控制）。

**为什么不做"撤销/改答"的通用能力**：实验只允许打分题重做，且不允许改选择题；把范围锁死，状态机才简单。

## 6. 数据层

### 6.1 表与索引

```sql

          presented_at, answered_at, elapsed_ms, retry_count, timed_out)

索引：
  responses(session_id, id)
  messages(session_id, seq)
  messages(session_id, visible_at)
  sessions(questionnaire_id, seq)
```

### 6.2 为什么 `items_json` 而不是拆表

题目的形态太多：

- 打分有 `min/max`；
- 单选/多选/排序有 `options`、`correct`；
- 文本有 `rows/maxLen/placeholder/variant/answer`；
- 题组有 `subs`（子题数组，子题又有自己的字段）；
- 消息有 `thinking`。

拆成关系表会得到 `items`、`item_options`、`item_subs`、`item_sub_options`……查询和保存都变复杂，而这个系统对题目的查询只有"整组读/整组写"。

**代价**：数据库无法校验 JSON 结构；只能靠 `normalizeItem` 在应用层兜底。`normalizeItem` 做了：

- 类型白名单；
- 参数按题型过滤 + 钳位（`normalizeLimits`）；
- 选项/子题/答案的默认值与清洗；
- 富文本生成（`html`）。

### 6.3 快照与"改题不影响进行中会话"

```js
// handleCreateSession
const session = store.createSession({
  questionnaireId: code,
  seq,
  items: questionnaire.items,   // 复制进 sessions.items_json
  userAgent: ...
});
```

`createSession` 内部 `JSON.stringify(items)` 写入。之后：

- `parseSession` 只读 `sessions.items_json`；
- 管理端改问卷只改 `questionnaires.items_json`；
- 两者彻底解耦。

### 6.4 数据库 pragma

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
PRAGMA temp_store = MEMORY;
```

- WAL：读写并发更好；写入不阻塞读；
- `synchronous=NORMAL`：减少 fsync，提交吞吐提升；
- `busy_timeout`：并发写时等 5 秒，而不是立刻报 `SQLITE_BUSY`；
- `temp_store=MEMORY`：临时表放内存。

### 6.5 迁移：`ensureColumn`

```js
function ensureColumn(table, col) {
  const cols = db.prepare(`PRAGMA table_info(${table})`).all().map(r => r.name);
  if (!cols.includes(col)) db.exec(`ALTER TABLE ${table} ADD COLUMN ${col} ...`);
}
```

这是"轻量迁移"：只加列，不重建表。早期还直接 `DROP TABLE` 旧表（重建式升级）。

**风险**：没有版本号、没有回滚、没有数据迁移脚本。生产升级前必须备份（含 WAL）。如果要长期维护，应该引入 `schema_version` 表 + 顺序 migration。

### 6.6 数据访问函数

`db.js` 导出大量具名函数，例如：

- 题目：`normalizeItems`、`matchAnswerLines`、`matchesAnswer`、`materialHtml`、`body16`
- 会话：`createSession`、`getSession`、`nextSessionSeq`、`touchSession`、`finishSession`、`abandonSession`
- 消息：`addMessage`、`listVisibleMessages`、`setClearSeq`、`maxMessageSeq`
- 作答：`addResponse`、`redoResponse`、`countAnswerUnits`、`unitFirstResponse`
- 报表：`listSessionSummaries`、`listResponseRows`、`listQuestionnaireSummaryRows`
- 账号：`createUser`、`verifyPassword`、`bumpTokenEpoch`

**没有 ORM**：SQL 直接写，函数即"仓储层"。优点是透明、好调优；缺点是没有类型/关系导航，改表要全局搜。

## 7. 前端架构

### 7.1 共同模式：状态对象 + 渲染函数

两套 SPA 都不是"组件树"，而是：

```js
const state = { ... };          // 全局状态
function renderX() { ... }      // 根据 state 生成/更新 DOM
async function api(path) { ... } // fetch 封装
```

被试端 `state` 的关键字段（`chat.js` 顶部）：

```js
{
  sessionId, action, busy, completed,
  seenMsgs,            // 已完整看过的消息数（重进只补播没看完的）
  serverOffsetMs,      // 服务端时间校准
  questionNodes,       // itemId -> 当前题卡 DOM
  answeredCount, totalAnswers, totalQuestions, currentQno,
  timeScale,           // 预览倍速
  showAnswered,        // 已答题是否显示
  draft,               // itemId -> 草稿
  deadlineFired, redoing
}
```

管理端 `state` 的关键字段（`admin.js` 顶部）：

```js
{
  token, user, meta,
  experiments, questionnaires,
  editingExp, editingQ, selected,
  sidebarMode, previewSpeed, dragId, view
}
```

> 【方法】不用框架也可以有"单向数据流"：所有变化先改 `state`，再调用渲染函数；不要到处直接改 DOM。这样至少能保证状态可追踪。

### 7.2 被试端的关键机制

| 机制 | 实现 | 目的 |
|---|---|---|
| 消息流 | `appendAiMessageAnimated` / `appendAiMessageStatic` | 打字机/思考面板；刷新后静态回放 |
| 题卡 | `renderQuestionCard` / `buildSubControl` | 10 种题型的控件统一构建 |
| 门控倒计时 | `serverNow()` + `action.availableAtMs/minSubmitAtMs/deadlineMs` | 只显示，不裁决 |
| 提交重试 | `postStep` + 0.4s/1.2s 退避 | 网络抖动不丢答案 |
| 草稿 | `localStorage`，键带问卷短码 + itemId | 文本不丢 |
| 恢复 | `loadStoredSession` / `renderResumeCard` | 刷新/退出续做 |
| 清屏 | `clearStream` + 世代号 `streamEpoch` | 防止旧异步续集写回新屏 |
| 重做 | `startRedo` / `submitRedo` / `settlePendingRedo` | 只改一张卡，不推进 |
| 预览桥 | `?preview=<id>` + `__preview` | 管理端 iframe 复用同一份被试端代码 |

**世代号**是一个值得学的细节：

```js
let streamEpoch = 0;
function beginFreshStream() { streamEpoch += 1; return streamEpoch; }
// 异步续集每次写屏前对 epoch，对不上就收手
```

它解决的是"提交后的一串异步播放还没结束，用户又触发了清屏/跳题"导致的串屏。没有它，旧消息会写进新页面。

### 7.3 管理端的关键机制

| 机制 | 实现 | 目的 |
|---|---|---|
| hash 路由 | `parseHash` / `handleRoute` | 列表/编辑/数据页切换，刷新不丢 |
| 编辑器 | `buildItemEditor` / `buildItemFields` / `buildParamSection` | 10 种题型 + 参数区 |
| 大纲 | `renderOutline` / `outlineVisibleIndexes` | 折叠、跳转、双向高亮 |
| 拖拽 | `startDrag` / `moveItem` | 题目排序 |
| 手机预览 | iframe + `openPreview` + 预览 API | 所见即所得，不落库 |
| 二维码 | `openQrModal` / `saveQrPoster` | 局域网分发 |
| 数据页 | 会话列表/个案/导出 | 研究者验收 |
| 布局 | 三栏可拖 + localStorage | 编辑效率 |

**编辑器与被试端是两套 UI**：编辑器里题目是卡片形态，被试端是消息流 + 题卡。不要试图复用同一套 DOM；共享的是**数据模型**（item JSON），不是组件。

### 7.4 富文本：前后端共用

`public/assets/richtext.js` 被：

- 浏览器 `<script>` 加载（管理端编辑器、被试端渲染）；
- `db.js` `require`（种子内容生成、服务端清洗）。

它保证"编辑器里看到的"和"服务端存的/被试端显示的"使用同一套清洗规则。这是同构代码的一个好例子。

## 8. 安全设计

### 8.1 管理端

| 风险 | 措施 |
|---|---|
| 密码泄露 | `scrypt` + 随机盐；不存明文 |
| 会话劫持 | HMAC-SHA256 签名 token；过期时间；`token_epoch` 单设备 |
| 未授权访问 | `requireUser` / `requireAdmin`；每个管理 API 先鉴权 |
| 越权看数据 | `canAccess(user, row)`：按创建者隔离 |
| 暴力破解 | 登录按 IP/账号限流；注册按 IP 限流 |
| 路径穿越 | `serveStatic` 解码后 `path.resolve` 校验必须落在 `public/` 内 |
| 大 body | `readJsonBody` 上限 4MB，超限 413 |
| XSS | 富文本白名单清洗 + CSP；但 CSP 含 `unsafe-inline/eval`（为截图工具），是已知弱化 |
| 点击劫持 | `frame-ancestors 'self'` |

### 8.2 被试端

| 风险 | 措施 |
|---|---|
| 猜链接 | 8 位不透明短码（不含 0/1/l/o），不可枚举 |
| 看答案 | 正确答案只在服务端；`itemDescriptor` 不下发 `correct` |
| 改时间 | 服务端时间戳 + 提交时校验；前端倒计时仅展示 |
| 刷新绕过清屏 | `clear_seq` 服务端过滤 |
| 重复提交 | `itemId` 幂等 |
| 跨问卷串会话 | `bootstrap` 校验 `session.questionnaire_id === code` |
| 被试数据泄露 | 管理端鉴权 + 数据隔离；导出需登录 |

### 8.3 需要知道的边界

- 被试端**没有登录**：拿到链接的人都能做。这是研究设计（一组一链）决定的，不是漏洞；防重复参加靠发放环节。
- `data.db` 含被试数据：**不能提交到 git、不能随便发人**。
- 便携包里的数据库快照会清空被试数据，但保留账号/模板/问卷；打包脚本要确保这一点。
- 管理端是"自用级"鉴权，不是多租户 SaaS；若要开放给外部研究者，需要更完整的账号/审计/隔离。

## 9. 质量保障架构

### 9.1 两层自检

| 脚本 | 层次 | 依赖实验内容？ | 作用 |
|---|---|---|---|
| `check-platform.js` | 平台行为 | 否（自带夹具） | 题型、门控、恢复、导出、鉴权等平台能力 |
| `consistency-check.js` | 内容配置 | 是 | 题数、量表、两组差异、反馈正文约束 |

`npm run check` 依次跑两层。项目文档记录过一次 74 项断言（平台 38 + 内容 36），以实际输出为准。

**为什么要分两层**：

- 改代码导致失败 → 平台层会报；
- 改内容导致失败 → 配置层会报，并提示"配置已变更？"；
- 否则你看到一片红，不知道是代码坏了还是文案改了。

### 9.2 时间旅行

门控测试最耗时的是"等 40 秒"。`scripts/lib/direct-db.js` 直接改：

- `sessions.pending_presented_at`
- `responses.presented_at`

让服务端认为时间已到。于是自检从 6 分 47 秒降到 0.7 秒，而且跑的是真实门控值（不是把 40 秒压成 1 秒）。

> 【方法】测试难，往往是因为状态不可控。把关键时间/状态存进数据库，测试就能"拨表"；存在内存/闭包里，就只能干等。

### 9.3 其他工具

| 工具 | 作用 | 注意事项 |
|---|---|---|
| `capture-shots.js` | 无头浏览器全流程截图 + DOM 断言 | 依赖本机 Chrome/Edge；部分软断言在干净 HEAD 上也失败，不能当唯一门禁 |
| `load-probe.js` | 单请求耗时、并发提交 | 本机数据，不代表生产 |
| `simulate-subjects.js` | 走真实接口灌模拟数据 | 会写库，别对生产库跑 |
| `sync-group-content.js` | 按种子重建两组预设问卷/模板 | 默认只预览，`--apply` 才写；写前备份 |
| `seed-thinking.js` | 把思考稿同步进已有问卷 | 幂等；建议停服务再跑 |

### 9.4 测试策略的取舍

- 没有单元测试框架：核心逻辑（状态机/门控）通过 API 集成测试覆盖；
- 没有 CI：本地 `npm run check`；这是单人项目的务实选择，但不是长期方案；
- UI 走查是"冒烟 + 截图"，不是像素级回归；
- 内容校验是"配置快照"，改内容会失败，需要同步更新断言。

## 10. 部署与分发架构

### 10.1 预实验便携包

```text
dist/预实验便携包.zip
  ├─ node.exe                 ← 目标机不用装 Node
  ├─ server.js / db.js / ...
  ├─ public/ / vendor/
  ├─ scripts/pilot-start.js
  ├─ 启动预实验.bat
  └─ data.db                  ← 当前库的只读快照，清空被试数据
```

`build-portable.js` 的关键动作：

1. 复制运行必需文件（不含 `node_modules`、不含开发脚本）；
2. 复制当前 `data.db` 快照；
3. 清空 `sessions` / `responses` / `messages`（保留模板/问卷/账号）；
4. 放入 `node.exe`；
5. 打 zip。

### 10.2 上线包

```text
dist/上线包.zip
  ├─ server.js / db.js / ...
  ├─ public/ / vendor/
  ├─ scripts/（运行所需）
  └─ 不含 node.exe、不含 data.db
```

部署流程（Windows Server，本站在用）：

```text
本地 npm run deploy
→ 上传 dist/上线包.zip 到 C:\apps\experiment-chat\update\
→ 运行 update.cmd nopause
   ├─ 备份 data.db（注意：WAL 三件套要一起备）
   ├─ 7-Zip 解压
   ├─ robocopy 覆盖（跳过 data.db、uploads）
   ├─ 结束旧 node
   ├─ 计划任务 LLM_in_dm 重启
   └─ 健康检查 http://127.0.0.1:3000/api/health
```

拓扑：

```text
被试/研究者 → HTTPS（nginx :443）→ 127.0.0.1:3000（Node 单进程）→ data.db
```

### 10.3 数据备份

**WAL 模式下 `data.db` 不是全部**：还有 `data.db-wal`、`data.db-shm`。备份/迁移必须三个一起，或先停服务再拷。

这是本项目踩过的真实坑：只拷主库，真实数据可能还在 WAL 里。

## 12. 架构评价：优点、局限、如果重做

### 优点

1. **依赖面极小**：没有 `node_modules`，离线/分发/供应链风险低。
2. **服务端权威**：门控、答案校验、清屏、幂等都在服务端，前端可替换。
3. **快照隔离**：改内容不影响进行中会话，实验可复现。
4. **数据模型贴合分析**：时间戳、选项标签、重试/超时、汇总宽表。
5. **可测试性**：时间戳落库，测试能"时间旅行"；两层自检区分代码/内容。
6. **交付完整**：便携包、上线包、部署文档、现场须知。

### 局限

1. `server.js` / `admin.js` 是单体大文件，改动成本随功能增长。
2. item JSON 无 schema，脏数据只能在运行时发现。
3. 迁移是"补列 + 删表"，没有版本化/回滚。
4. 手写 xlsx / 清洗器 / 测试框架，长期维护成本高。
5. CSP 为截图工具放宽了 `unsafe-inline/eval`。
6. 单机 SQLite，无法水平扩展。
7. 内容有两份来源（种子 + 线上库），需要同步脚本，存在漂移风险。
8. 前端无组件化，复杂交互靠约定。

### 如果重做，我会怎么改

- 保留：统一题目模型、服务端门控、会话快照、零依赖交付。
- 改：
  - 服务端拆 `routes/` + `services/` + `state-machine.js`；
  - item 用 JSON Schema/zod 校验；
  - 引入版本化 migration；
  - 管理端上 Vite + React（被试端保持原生）；
  - 测试换 Playwright + Vitest，但保留 direct-db 时间旅行；
  - CI 跑 `npm run check`；
  - 内容以管理端为唯一源，种子只用于首次初始化；
  - 收紧 CSP，截图工具改用 CDP 求值。

> 【方法】架构复盘不要只说"哪里不好"，要说"当时为什么这么选、什么条件下会改"。这才是工程判断。
