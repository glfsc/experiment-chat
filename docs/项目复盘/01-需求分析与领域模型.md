# 01 · 需求分析与领域模型

> 目标：看完这一篇，你能拿到一份"实验程序表"或一段业务描述，独立把它变成**可开发、可验收、可分析**的软件需求，并画出实体与状态。
>
> 这一篇不急着写代码。需求阶段写错一个字，后面要用几百行代码去还债。

---

## 0. 先给结论

这个项目表面上叫"实验对话系统"，但它的本质不是"做一个聊天页面"，而是：

> **把一份受控的行为实验程序，变成一条可重复执行、可审计、可直接出数据的数据生产流水线。**

这句话决定了后面所有设计：

- 为什么每个时间点都要服务端记录？因为"受控"意味着不能靠被试自觉。
- 为什么题目要快照？因为"可重复"意味着中途改问卷不能污染正在跑的被试。
- 为什么导出要一被试一行？因为研究者拿到数据就要跑统计，不想再做数据清洗。
- 为什么两组内容要逐字校验？因为组间唯一差异就是操纵，多一个字都是混淆变量。

如果你只记住一句话：**实验系统的第一性原理是"控制"，不是"功能"。**

## 1. 原始需求：研究设计与实验材料

### 1.1 需求从哪里来

原始材料是两份 Word 文档（`demand/` 目录）：

- 《组别3-AI反馈+目标清晰度高》
- 《组别4-AI反馈+目标清晰度低》

它们不是软件需求文档，而是**实验程序表**：规定实验助理在第几步说什么、被试做什么、等多久、记什么。软件要做的，是把这个"人肉执行"的过程自动化。

### 1.2 研究设计拆解

先别急着看界面。把研究设计翻译成一张变量表：

| 维度 | 内容 |
|---|---|
| 研究问题 | 面对 AI 的负面反馈，个体的创造力会提升还是下降？目标清晰度是否调节这一过程？ |
| 实验设计 | 2 组被试间设计：目标清晰度高（组别3）/ 低（组别4）；所有被试都接受同一条标准化负面反馈 |
| 自变量（操纵） | 任务要求的详细程度：高清晰度组有 6 条创作要求 + 100 分评价标准；低清晰度组只有 2 条极简要求 |
| 组内重复 | 第一次创作 → 负面反馈 → 第二次创作（同一任务） |
| 因变量 | 第二次广告语的创造力（后续由专家评分/文本分析）；反馈公平性（6 题）；元过程（5 题）；任务过程（4 题） |
| 操纵检验 | 目标清晰度 5 题；注意力检测 1 题；反馈来源识别 1 题 |
| 其他测量 | 反馈效价/准确性感知 2 题 |
| 伦理 | 知情同意；结束时的欺骗事后解释（debrief） |
| 关键控制 | 所有被试收到**完全相同**的负面反馈；反馈在提交后延迟出现；强制阅读；两次创作时限一致 |

这张表里已经藏着三个软件需求：

1. **组别不能被试自己选**：研究者发哪条链接，被试就进哪组。系统不做随机分组。
2. **反馈必须是固定文本**：不是真调 LLM，不能因被试作品而变化，否则操纵不标准化。
3. **时间必须可控**：延迟出现、强制阅读、创作窗口，都要能配、能执行、能记录。

> 【方法】拿到任何实验方案，先做这张"变量—操纵—测量"表。软件需求 80% 从这张表里长出来，而不是从界面截图里长出来。

### 1.3 把实验流程表读成"时间线"

原始文档的九节流程，可以压缩成下面这条被试时间线（括号里是系统需要记录的东西）：

```text
欢迎语 / 任务信息（何时呈现）
→ 任务要求（高/低两个版本）
→ 阅读材料确认（被试输入指定句子才能继续）
→ 目标清晰度 5 题（每题的选择 + 呈现/作答时间）
→ 创作指引（8 分钟内完成，开始 2 分钟后才可提交）
→ 第一次广告语 + 创作说明（文本、提交时间、耗时）
→ 负面反馈（先思考 20 秒，再流式输出正文）
→ 阅读反馈确认（强制停留 30/40 秒 + 输入指定句子）
→ 注意力检测 1 题（正确答案不下发）
→ 反馈来源识别 1 题
→ 反馈公平性 6 题 → 效价 2 题 → 元过程 5 题（进入本节先清屏）→ 任务过程 4 题
→ 第二次任务说明 + 任务要求（与开头一致）
→ 第二次广告语 + 创作说明（同样 2 分钟可交、8 分钟截止）
→ 结束说明（欺骗解释）
```

> 【方法】把文档里的"第 1 节、第 2 节……"改写成"被试在这一刻看到什么、能做什么、系统记什么"。**时间线比章节号更接近软件**。

### 1.4 原流程为什么必须被替换

如果继续用 QQ 群 + 人工计时，会出现这些问题：

| 风险 | 后果 | 软件对应能力 |
|---|---|---|
| 实验助理发消息的时间不一致 | 被试间等待时长不同，混淆 | 服务端统一计时 |
| 被试提前提交 | 创作时间不足，数据不可比 | 最短提交时间门控 |
| 被试不看反馈就答题 | 操纵失效 | 强制阅读 + 阅读确认 |
| 人工记录答案 | 错录、漏录、无法算耗时 | 逐题落库 + 自动导出 |
| 两组材料被误改 | 组间差异不止操纵 | 内容逐字校验 |
| 现场断网/没装环境 | 实验开不了 | 离线局域网 + 便携包 |
| 被试刷新/退出 | 进度丢失、重复作答 | 会话恢复 + 幂等提交 |

这张表就是"非功能需求"的来源。**功能需求回答"能做什么"，非功能需求回答"在什么条件下必须可靠"。**

## 2. 从实验材料到软件需求

### 2.1 先识别角色

| 角色 | 关心什么 | 系统里对应 |
|---|---|---|
| 研究者 / 实验助理 | 编排内容、发链接、现场不出错、最后拿到能跑统计的数据 | 管理端（登录、模板、问卷、预览、数据、导出） |
| 被试 | 打开就能做、手机上能读能点、中断能续、不被莫名其妙卡住 | 被试端（`/chat?q=短码`） |
| 系统（引擎） | 按顺序呈现、按时间放行、按规则校验、把每一步记下来 | 服务端状态机 + 数据层 |
| "AI 小A" | 是一个**被扮演的角色**，不是真模型 | 固定文案 + 思考稿 + 流式呈现参数 |

特别强调最后一行：**这里的 AI 是实验刺激，不是产品功能。** 因此：

- 不能接真实 LLM 随机生成反馈——那会引入无法控制的方差；
- "思考过程"也是预先写好的稿子，只是按字数铺开发出，让被试觉得像真 AI；
- 反馈正文、思考稿、呈现时长都是**实验材料**，要能版本化、能校验。

> 【方法】角色表里一定要有"系统"这个非人类角色。很多需求（幂等、快照、门控）只有在"系统要保证什么"这一栏才会被写出来。

### 2.2 功能需求清单（FR）

下面这份清单是"从流程反推"的示例，不是让你照抄。注意每条都带**验收口径**，否则开发完无法判断做没做对。

#### A. 实验编排（研究者侧）

| 编号 | 需求 | 优先级 | 验收口径 |
|---|---|---|---|
| FR-A1 | 能把一套实验保存为可复用的"题目模板" | P0 | 新建/复制/改名/删除；插入问卷时整组复制，之后互不影响 |
| FR-A2 | 能新建问卷，一条链接对应一份问卷 | P0 | 问卷有 8 位不透明短码；`/chat?q=短码` 可进入 |
| FR-A3 | 支持 10 种题型：消息、知情同意、阅读确认、结束说明、题组、打分、单选、多选、文本、排序 | P0 | 每种题型能插入、编辑、保存、在被试端正确渲染 |
| FR-A4 | 题目能配参数：强制等待、最短提交、最长作答、思考时长、流式速度、清屏点、允许重做 | P0 | 参数只配在题目上；不配则回落到代码默认值；编辑器能增删改 |
| FR-A5 | 题目支持 1–4 级大纲分组 | P1 | 只影响管理端大纲，不影响被试端顺序 |
| FR-A6 | 编辑器有手机实时预览，能按真实节奏试填 | P1 | 预览不建真实会话、不落库；支持倍速与跳题 |
| FR-A7 | 两组预设问卷只允许在"任务要求"等处不同 | P0 | 同步脚本逐字段比对，差异数量与位置可断言 |

#### B. 被试流程

| 编号 | 需求 | 优先级 | 验收口径 |
|---|---|---|---|
| FR-B1 | 被试打开链接即建会话，按进入顺序编号 | P0 | 同一问卷 `seq` 递增；换设备新建会话，旧会话保留 |
| FR-B2 | 消息类题目按顺序自动发出，支持打字机/思考面板 | P0 | 刷新后只补播没看完的部分；思考稿播完不可回看（本研究设定） |
| FR-B3 | 非消息题形成"作答单元"，一次提交一条记录 | P0 | 题组的多道子题同属一个单元，落多行、`sub_index` 区分 |
| FR-B4 | 强制等待未到、最短提交未到，服务端拒绝 | P0 | 提前提交返回 400 `too_early`，带放行时刻；前端只做倒计时展示 |
| FR-B5 | 最长作答到点，有内容自动提交，无内容停在题上 | P0 | 自动提交与手动提交走同一校验；无内容不产生空记录 |
| FR-B6 | 相邻且参数相同的题共用一个作答窗口 | P1 | 第二题显示"与上一题共用窗口"；起点取该段首题 |
| FR-B7 | 刷新/退出后可在恢复窗口内续做 | P0 | 同一浏览器凭 localStorage 恢复；超窗/换设备新建 |
| FR-B8 | 重复提交/迟到请求不能记到下一题 | P0 | `itemId` 不匹配当前题时幂等忽略，返回当前状态 |
| FR-B9 | 清屏点：呈现某题前清空聊天流，刷新也看不到之前内容 | P1 | 清屏点记在服务端 `clear_seq`；数据仍完整保留 |
| FR-B10 | 打分题可单独重做，只更新原记录 | P1 | 不产生重复行；刷新后不再提供重做；同屏最多一张卡重做中 |
| FR-B11 | 文本题可要求输入指定内容才能发送 | P1 | 服务端比对；失败不落库、不进聊天流；标准答案不下发 |
| FR-B12 | 被试端适配手机，正文可读、按钮可点 | P0 | 375px 宽度下无横向滚动；关键按钮≥44px |

#### C. 数据与导出

| 编号 | 需求 | 优先级 | 验收口径 |
|---|---|---|---|
| FR-C1 | 每次作答记录呈现时间、作答时间、耗时、重试、超时 | P0 | 每行都有；服务端时间为准 |
| FR-C2 | 会话有状态：进行中/已完成/已作废 | P0 | 超时无操作可作废并释放设备；作废默认不进导出 |
| FR-C3 | 一键导出 Excel，含汇总/逐题/明细 | P0 | 汇总一被试一行；量表逐题原始分；两次作品文本；选择题对错 |
| FR-C4 | 汇总表含"被试自填编号" | P0 | 取自知情同意页填写的编号，不是会话序号 |
| FR-C5 | 导出能直接进统计软件 | P0 | 列名稳定、无合并单元格、无公式依赖；缺失值有统一表示 |

#### D. 运营与安全

| 编号 | 需求 | 优先级 | 验收口径 |
|---|---|---|---|
| FR-D1 | 管理端登录；账号分管理员/普通主试 | P0 | 密码 scrypt 加盐；未登录不能调管理 API |
| FR-D2 | 同一账号单设备在线 | P1 | 别处登录/改密后旧 token 立即失效 |
| FR-D3 | 数据按创建者隔离 | P0 | A 账号看不到 B 账号的模板/问卷/数据 |
| FR-D4 | 局域网内手机扫码直达对应问卷 | P1 | 管理端生成二维码；地址自动取手机可达 IP/域名 |
| FR-D5 | 双击启动，目标电脑不装 Node 也能跑 | P1 | 便携包内置 `node.exe`；端口冲突自愈 |
| FR-D6 | 公网部署可一键更新、自动备份 | P1 | 上线包不含数据库；更新脚本备份→覆盖→重启→健康检查 |

#### E. 质量保障

| 编号 | 需求 | 优先级 | 验收口径 |
|---|---|---|---|
| FR-E1 | 一条命令跑平台行为自检 | P0 | 不依赖实验内容；覆盖题型、门控、恢复、导出 |
| FR-E2 | 一条命令校验实验内容 | P0 | 题数、量表、两组差异、反馈正文约束 |
| FR-E3 | 无头浏览器走查关键界面 | P2 | 截图 + 断言；失败不一定是发布门禁，但要能看出崩坏 |
| FR-E4 | 并发探针 | P2 | 能测单请求耗时与并发提交成功率 |

> 【方法】写 FR 时用"动词 + 对象 + 可观察结果"。不要写"支持计时"，要写"提前提交时服务端返回 400，且不落库"。**没有验收口径的需求，等于没写。**

### 2.3 非功能需求（NFR）

| 类别 | 要求 | 本项目的落地方式 |
|---|---|---|
| 性能 | 几百人同时在线不崩 | 单请求 ~2ms；一位被试全程约 27–31 次请求；无轮询；WAL |
| 可用性 | 实验现场无外网也能跑 | 局域网 + 便携包 + 内置 node |
| 可靠性 | 刷新/断网/误关页不丢进度 | 逐题提交、localStorage 恢复、提交重试、草稿 |
| 数据完整性 | 不能重复、不能串题、不能改历史 | 当前题 `itemId` 幂等校验、会话快照、就地更新重做 |
| 安全 | 被试数据不被未授权访问 | 管理端鉴权、数据按创建者隔离、路径穿越防护、限流 |
| 隐私 | 被试编号/作品匿名保存 | 不采集额外身份信息；导出可控；debrief 说明 |
| 可维护性 | 内容改动不必改代码 | 题目模板 + 管理端编辑 + 种子/同步脚本 |
| 可移植性 | Windows 服务器/笔记本都能跑 | 零依赖、单进程、单文件库 |
| 可审计 | 能解释每个数字怎么来的 | 时间戳、选项标签、重试/超时、状态 |
| 可复现 | 同一份问卷对每个人都一样 | 题目快照 + 固定反馈 + 内容校验 |

### 2.4 约束条件（比需求更容易被忽略）

- **现场约束**：实验可能在教室/实验室，网络不稳定，研究者不一定懂命令行。
- **设备约束**：被试大多数用手机，屏幕小、浏览器各异、可能中途锁屏。
- **人员约束**：开发只有一个人 + AI，维护成本必须低；不能引入需要长期升级的依赖。
- **时间约束**：预实验有明确日期，先保证能收数据，再谈体验。
- **伦理约束**：知情同意、欺骗事后解释、数据匿名，都是硬约束，不是"以后再加"。
- **内容约束**：实验材料会反复改（文案、时长、题目顺序），系统必须让研究者自己改，而不是每次找开发。

> 【方法】把约束写成"如果违反，实验会怎样失败"。例如"不能联网"不是偏好，而是"现场没有外网，违反则无法开实验"。这样优先级自然就出来了。

## 3. 隐藏需求：需求文档不会写，但一定会发生

这一节是本项目最值钱的部分。下面每一条，都是实际开发/预实验中踩出来的。

### 3.1 时间：谁说了算？

**表面需求**："30 秒后发送反馈。"
**隐藏问题**：

- 用前端 `setTimeout`？被试改系统时间、切后台、刷新，都能绕过。
- 用轮询问服务器"到点了吗"？几百人会产生大量无意义请求。
- 被试提前点提交怎么办？前端置灰不可靠，必须服务端拒绝。

**本项目的解法**：

- 服务端记录 `presented_at`，计算 `availableAt / minSubmitAt / deadline`；
- 前端只负责显示倒计时，提交时服务端二次校验；
- 提前提交返回 `400 too_early`，带 `availableAt`，前端据此继续倒计时；
- 不做轮询：被试读题、打字、看倒计时期间**零请求**。

> 【方法】任何"到点才能做"的需求，先问：**时间基准在哪？谁能改？失败时返回什么？** 这三问答不上来，就不要写前端计时。

### 3.2 中断：刷新、锁屏、换设备

**表面需求**："被试可以刷新。"
**隐藏问题**：

- 刷新后消息会不会重播？已答的题会不会丢？倒计时会不会重置？
- 换手机/清缓存后，是继续还是新开？旧会话怎么处理？
- 同一台电脑连着做多个被试，怎么释放设备？

**本项目的解法**：

- 会话 ID 存 localStorage（键里带问卷短码）；
- `GET /api/bootstrap?session=` 返回可见消息、当前作答单元、剩余门控；
- 恢复窗口默认 24 小时，可在管理端改；超窗则新建会话，旧会话保留；
- 进入结束说明页视为释放设备，清本机记录；`&fresh=1` 可强制新开。

> 【方法】画一张"异常路径图"：刷新、断网、锁屏、换设备、重复提交、超时、管理员改题。每条路径都要有明确结果，不能留"看情况"。

### 3.3 数据口径：编号到底是谁的编号？

**表面需求**："记录被试编号。"
**隐藏问题**：

- 是系统按进入顺序自动编的号（`sessions.seq`），还是被试在知情同意页自己填的号？
- 导出时用哪个？如果两个都有，列名怎么区分？
- 被试填的号要不要去重/校验？

**本项目的解法**：

- 两个都保留：`seq` 是内部序号；自填编号落在 `responses.value_text`；
- 汇总表新增"被试自填编号"列；
- 自填编号不校验、不去重（研究设计如此）。

> 【方法】凡是"编号、时间、分数、组别"这类词，都要追问：**口径、来源、缺失值、是否可重复**。数据口径错一次，整批数据可能白跑。

### 3.4 内容变更：改一个字，影响谁？

**表面需求**："研究者可以随时改问卷。"
**隐藏问题**：

- 改了题目，正在做的被试会怎样？
- 已经做完的被试，数据还能对应上吗？
- 两组预设问卷怎么保证只差操纵？

**本项目的解法**：

- 会话创建时把题目**快照**进 `sessions.items_json`，之后改模板/问卷不影响进行中的会话；
- 种子内容集中在 `seed-content.js`，已有问卷用同步脚本更新；
- `sync-group-content.js` 逐字段比对，只允许"任务要求"等指定差异；
- 自检失败时提示"配置已变更？"，区分代码坏了还是内容改了。

> 【方法】内容型系统一定要区分"模板/版本"和"运行中实例"。**快照**是最便宜、最可靠的隔离手段。

### 3.5 防作弊：哪些能防，哪些不能防

**表面需求**："防止被试乱答。"
**隐藏问题**：

- 切屏能拦截吗？移动端浏览器没有这个权限，只能检测 + 提醒。
- 刷新能阻止回看吗？如果内容只在客户端清空，刷新就全回来了。
- 标准答案能下发吗？不能，否则被试直接看。

**本项目的解法**：

- 清屏点记在服务端 `clear_seq`，刷新也拿不到清屏前消息；
- 标准答案只在服务端比对，失败提示可自定义，答案不下发；
- 切屏只做 `visibilitychange` 提醒，不叠加 `beforeunload`（避免和关闭流程打架）；
- 接受"防不住所有作弊"，把能记录的行为记下来（重试、超时、切屏提醒次数可扩展）。

> 【方法】安全需求要写"防到什么程度、防不住时怎么办"。研究场景里，**记录**往往比**拦截**更现实。

### 3.6 现场运维：双击之后发生什么

**表面需求**："给实验助理一个能用的包。"
**隐藏问题**：

- 目标电脑没装 Node 怎么办？
- 双击两次会不会起两个服务？
- 3000 端口被别的软件占了怎么办？
- 手机连不上，是防火墙、热点、还是 AP 隔离？
- 打包时怎么保证不带走上一个被试的数据？

**本项目的解法**：

- 便携包内置 `node.exe`，只带运行必需文件；
- 启动器先结束旧实例，端口冲突自动换空闲端口，二维码跟着新端口走；
- 数据库取当前库的**只读快照**，只清空被试数据（会话/作答/消息），保留模板/问卷/账号；
- 现场排障写成 `实验人员须知.txt`（热点、防火墙、AP 隔离、四步检查）。

> 【方法】交付物不是"代码能跑"，而是"目标用户在目标环境里能独立跑"。**把运维步骤当成需求写。**

### 3.7 伦理：知情同意与欺骗解释

- 知情同意页必须能勾选同意，可选填被试编号；
- 结束说明必须解释"反馈是标准化预设，不是针对你个人"，并给联系方式；
- 数据匿名保存，仅用于学术分析；
- 这些不是"文案"，是流程节点：不确认不能进入，不读结束说明会话不算完成。

> 【方法】涉及人的研究，伦理节点要作为**状态机的一部分**，不能只是页面上的几行字。

## 4. 需求歧义与决策记录（ADR）

需求阶段最重要的产出不是"需求列表"，而是**决策记录**：当时有哪些选项、为什么选这个、代价是什么。下面挑本项目真实的几组。

### 4.1 分组与链接

| 问题 | 选项 | 决定 | 理由 |
|---|---|---|---|
| 一人一链还是每组一链？ | 一人一链（可追踪身份）/ 每组一链（简单） | 每组一链 | 研究设计不需要身份；发放哪条链接即入组；实现简单、现场不易发错 |
| 是否自动随机分组？ | 系统随机 / 研究者预分配 | 研究者预分配 | 实验助理按批次控制；系统不做随机化，避免"刷新换组" |
| 短码是否暴露组别？ | 用 `group3/group4` / 不透明码 | 8 位不透明码（不含 0/1/l/o） | 被试看不出组别，减少需求特征 |

### 4.2 超时未作答

| 选项 | 结果 | 决定 |
|---|---|---|
| 到点自动提交空答案 | 数据完整，但会产生大量空值，且被试可能没来得及写 | 不做 |
| 到点停在题上，提示"请完成作答后提交" | 被试可能卡住，需要现场兜底 | **采用**（明确记录为已知风险） |
| 到点后允许"重试"开新窗口 | 给被试补救机会，但会改变时间操纵 | 提供重试，并记录 `retry_count` / `timed_out` |

> 这是典型的"产品正确 vs 实验正确"冲突。最后选择保留现状，并在实施报告里写明"现场需要人工兜底流程"。**决策记录的价值在于：以后有人问"为什么不做"，你有答案。**

### 4.3 延迟 30 秒 vs AI 思考面板

原始文档要求"提交后 30 秒发送反馈"。后来为了让人机对话更自然，加了"AI 思考过程"面板。

- 如果两者并存：被试先干等 30 秒，再看到"已思考 8 秒"，逻辑矛盾；
- 决定：**删除延迟参数**，等待时间由思考面板承担；
- 代价：如果将来又需要"延迟 N 秒再发消息"，要重新加回（代码可回滚，但能力被移除）。

> 【方法】两个需求实现同一效果时，不要叠加，要**替换并删除旧路径**。否则作者每次都要判断"到底哪个在生效"。

### 4.4 问卷级默认值 vs 题目级参数

早期是"问卷默认 + 题目覆盖"两层。作者经常算不清某题到底生效哪个值。

- 决定：删除问卷级默认值，参数只配在题目上，未配置回落到代码常量 `DEFAULT_LIMITS`；
- 代价：作者要多点几次"添加参数"；换来的是**单一事实来源**。

> 【方法】配置系统里，每多一层"默认值"，就多一层解释成本。优先做"一层 + 代码默认"。

### 4.5 题卡 vs 消息气泡

"全流程对话化"听起来应该把每道题做成聊天气泡。实际做的是"题卡 + 底部输入框"的混合形态。

- 原因：题卡整体改气泡会重写截图走查的全部选择器，风险与收益不成比例；
- 决定：圈圈头像、常驻输入框、默认不隐藏、降权呈现都做；题卡保留；
- 记录为"部分完成"，而不是假装做完了。

> 【方法】需求可以"部分完成"，但必须**明确边界和原因**。这比"看起来都做了"更专业。

### 4.6 一个账号多设备

- 早期允许，后来发现同一账号在多端改同一份问卷会互相覆盖；
- 决定：一账号单设备，用 `token_epoch` 实现"别处登录/改密，旧设备立即失效"；
- 代价：研究者换电脑要重新登录；换来的是数据一致性。

### 4.7 切屏记录

- 需求："退出/切屏提醒"；
- 选项：只提醒 / 提醒 + 记录次数与时长；
- 决定：只提醒（第一版），记录作为可扩展项；
- 理由：移动端无法拦截，记录会增加隐私与实现复杂度，先不做。

> 【方法】把"不做"也写进决策记录。**范围管理不是砍需求，是明确这次不做什么、为什么。**

## 5. 领域模型：把需求变成实体

### 5.1 从名词开始

把实验材料里的名词圈出来：

> 实验、组别、题目、材料、量表、反馈、被试、会话、作答、时间、链接、编号、导出。

去掉同义词、合并近义词，得到核心实体：

| 实体 | 一句话定义 | 本项目表 |
|---|---|---|
| 题目（item） | 系统呈现的最小单位，可以是消息、页面或一道题 | 存在 `experiments.items_json` / `questionnaires.items_json` / `sessions.items_json` |
| 实验模板（experiment） | 一套可复用的题目组合 | `experiments` |
| 问卷（questionnaire） | 一条链接 + 一列题目 | `questionnaires` |
| 会话（session） | 一位被试的一次完整作答过程 | `sessions` |
| 消息（message） | 聊天流里的一条 AI/用户消息 | `messages` |
| 作答（response） | 一个作答单元的结果 | `responses` |
| 设置（setting） | 恢复窗口、作废时长等全局配置 | `settings` |
| 用户（user） | 管理端账号 | `users` |

### 5.2 关键抽象：一切皆题目

这是整个项目最重要的设计决定。

**没有**"实验表、流程表、量表表、材料表、问卷题目表"这一堆概念，只有 `item`：

- 消息是 item（`type: message`）；
- 知情同意是 item（`type: gate`）；
- 阅读确认是 item（`type: confirm`）；
- 结束说明是 item（`type: debrief`）；
- 打分/单选/多选/文本/排序/题组都是 item。

实验模板 = 一组 item；问卷 = 一条链接 + 一组 item；会话 = 创建时复制的一组 item。

**为什么这样设计？**

1. **流程可变**：研究者会改题目顺序、插入量表、删掉某节。硬编码流程意味着每次改流程都要改代码。
2. **渲染统一**：管理端大纲、被试端卡片、预览、导出都遍历同一个数组，不用为每种"板块"写一套逻辑。
3. **复用**：实验模板可以整组插入问卷；题目可以复制、拖动、批量插入。
4. **参数统一**：等待、最短提交、最长作答、清屏、思考时长都挂在 item 上，不需要"问卷级/流程级/题目级"三套配置。

**代价**：

- item 是异构 JSON（不同题型字段不同），数据库层面无法强约束；
- 编辑器要处理 10 种题型的字段与二级形态，复杂度集中在管理端；
- "消息"和"题目"混在一个数组里，统计题号时要单独过滤（`QUESTION_TYPES`）。

> 【方法】当业务里存在大量"结构相似、字段不同"的流程节点时，考虑"统一节点 + 类型 + 参数"的模型。它比"每种节点一张表"更灵活，但要把校验放在应用层。

### 5.3 十种题型与两个维度

不要按"业务场景"分题型（量表、创作、材料），要按**呈现/作答方式**分：

| 类型 | 作用 | 是作答单元？ | 占题号？ | 可配参数（节选） |
|---|---|---|---|---|
| `message` | 纯呈现：任务信息、指导语、反馈 | 否 | 否 | 清屏、思考时长、流式速度 |
| `gate` | 知情同意（可带编号） | 是 | 否 | 清屏 |
| `confirm` | 阅读确认页（停留 N 秒后可点） | 是 | 否 | 清屏、强制等待 |
| `debrief` | 结束说明 | 是 | 否 | 清屏 |
| `group` | 题组：多子题一次提交 | 是 | 是 | 等待、最短/最长、清屏 |
| `rating` | 打分（量表） | 是 | 是 | 等待、最短/最长、清屏、重做 |
| `single` | 单选（可设正确答案） | 是 | 是 | 等待、清屏 |
| `multi` | 多选 | 是 | 是 | 等待、清屏 |
| `text` | 文本（自由/需输入指定内容） | 是 | 是 | 等待、最短/最长、清屏 |
| `rank` | 排序 | 是 | 是 | 等待、清屏 |

两个容易混淆的维度：

- **是否作答单元**：决定状态机推进时是否要等被试提交；
- **是否占题号**：决定被试看到的"第 N 题"和进度条分母。

消息、知情同意、确认页、结束说明都**不占题号**；其中后三者仍是作答单元（要等确认）。这个区分直接来自实验文档：文档里的"第 1 节"不等于"第 1 题"。

> 【方法】建模时把"呈现形态"和"业务语义"分开。否则你会为"量表""创作""材料"各写一套类型，最后发现它们只是参数不同。

### 5.4 会话快照：运行中实例与模板解耦

```text
问卷（模板） items_json ──复制──▶ 会话 items_json（快照）
                                      │
                                      ├─ 消息流 messages
                                      └─ 作答 responses
```

- 被试进入时，服务端把问卷的 items 复制进 `sessions.items_json`；
- 之后研究者改问卷/模板，进行中的会话不受影响；
- 会话里的消息、作答都带 `item_id`，可以回溯到当时的题目。

**为什么不用外键实时关联？**

- 实验要求可复现：同一被试看到的材料不能在他作答期间被改掉；
- 内容会持续修订（文案、时长），实时关联会让"第 5 题"在不同时间指向不同内容；
- 快照的存储成本很低（几 KB JSON），换来的是数据可解释性。

> 【方法】凡是"模板会被编辑、实例正在运行"的系统（问卷、合同、工单、审批流），都优先考虑实例快照。

### 5.5 状态机

被试端的核心不是"页面跳转"，而是"作答单元推进"。

```text
                 ┌─────────────────────────────┐
                 │  GET /api/bootstrap          │
                 │  有 session？                │
                 └──────────┬──────────────────┘
                            │ 否
                            ▼
                 ┌─────────────────────────────┐
                 │  POST /api/session           │
                 │  复制题目快照、分配 seq      │
                 │  发出首个单元之前的消息      │
                 └──────────┬──────────────────┘
                            │
                            ▼
        ┌───────────────────────────────────────┐
        │  当前单元 unit[completedCount]        │
        │  computeAction() 计算门控与题面       │
        └──────────┬────────────────────────────┘
                   │ 被试提交 POST /api/step
                   ▼
        ┌───────────────────────────────────────┐
        │  1. 会话进行中？                      │
        │  2. itemId == 当前题？（幂等）        │
        │  3. 强制等待/最短提交到了吗？         │
        │  4. validateAnswer() 校验答案         │
        │  5. 写 responses + 用户回显消息       │
        │  6. 发出下一单元之前的消息            │
        │  7. 处理清屏点                        │
        │  8. completedCount+1，计算下一动作    │
        └──────────┬────────────────────────────┘
                   │
        还有单元？ ─┴─ 没有了 → finishSession()，completed
```

关键不变量：

1. 一个会话同一时刻只有一个"当前单元"；
2. 提交必须携带当前单元的 `itemId`，否则幂等忽略；
3. 所有时间门控以服务端时间与 `presented_at` 为准；
4. 消息只在"从前一单元到当前单元"之间发出，重复调用不会重复发；
5. 清屏点记在服务端，刷新不能绕过。

### 5.6 计时模型（最容易写错的部分）

设：

- `presented` = 当前单元的呈现时刻；
- `wait` = 作答前强制等待秒数；
- `minSubmit` = 最短提交秒数；
- `maxAnswer` = 最长作答秒数。

则：

```text
availableAt = presented + wait
minSubmitAt = windowStart + minSubmit
deadline    = windowStart + maxAnswer
```

其中 `presented` 不是"页面加载时间"，而是：

```text
presented = max(上一单元作答完成时间, 最近一条消息时间, 当前时间)
```

**共用窗口**：如果当前题与前面相邻的题 `minSubmit/maxAnswer` 完全相同，则取这一连续段首题的 `presented_at` 作为 `windowStart`。这样"广告语 + 创作说明"两道题共用一个 2 分钟/8 分钟窗口，而不是各算一次。

**服务端校验**：

```js
if (action.availableAtMs && now < action.availableAtMs) return 400 too_early;
if (action.minSubmitAtMs && now < action.minSubmitAtMs) return 400 too_early;
if (action.deadlineMs && now > action.deadlineMs + GRACE) { /* 超时处理 */ }
```

> 【方法】计时需求要写成公式，不要写成"大约""之后"。公式能直接变成测试用例：给定时钟与呈现时刻，断言放行/拒绝。

### 5.7 数据模型与"为分析而设计"

核心表（简化）：

```text
experiments(id, name, items_json, owner_id, created_at, updated_at)
questionnaires(id, title, items_json, owner_id, created_at, updated_at)
sessions(id, questionnaire_id, seq, status, started_at, ended_at, duration_sec,
         items_json, pending_presented_at, active_at, retry_json, clear_seq, owner_id)
messages(id, session_id, role, content, seq, created_at, thinking, think_ms, type_ms, item_id)
responses(id, session_id, item_id, item_index, item_type,
          unit_index, sub_index, value, value_text, option_label,
          presented_at, answered_at, elapsed_ms, retry_count, timed_out)
settings(key, value)
users(id, username, pass_hash, salt, role, avatar, token_epoch, ...)
```

设计要点：

| 设计 | 原因 |
|---|---|
| `items_json` 存整组题目 | 题目异构、嵌套（题组子题），关系表会爆炸；整组读写更简单 |
| `sessions.items_json` 快照 | 保证实验可复现 |
| `responses.unit_index + sub_index` | 题组一次提交多行；统计时能还原"第几个作答单元 / 第几个子题" |
| `value` + `value_text` + `option_label` | `value` 便于统计（数字）；`value_text` 存文本/多选/排序的原始结构；`option_label` 便于人读与导出 |
| `presented_at / answered_at / elapsed_ms` | 行为分析需要；也是门控的依据 |
| `retry_count / timed_out` | 记录异常行为，不要只留"最终答案" |
| `clear_seq` | 清屏点必须服务端记，否则刷新绕过 |
| `token_epoch` | 一账号单设备；改密/登出/别处登录立即失效 |

**为分析而设计**：不要等导出时再拼字段。研究变量在落库时就要有对应字段：

| 研究变量 | 操作化 | 落库位置 | 导出列 |
|---|---|---|---|
| 组别（目标清晰度高/低） | 问卷 ID / 预设分组 | `sessions.questionnaire_id` | 组别 |
| 目标清晰度检验 | 5 道打分题 | `responses.value` | 5 列原始分（或均分） |
| 第一次作品 | 文本题/题组 | `responses.value_text` | 第一次广告语、创作说明 |
| 第二次作品（因变量） | 文本题/题组 | `responses.value_text` | 第二次广告语、创作说明 |
| 反馈公平性 | 6 道打分题 | `responses.value` | 6 列/均分 |
| 元过程 | 5 道打分题 | `responses.value` | 5 列/均分 |
| 任务过程 | 4 道打分题 | `responses.value` | 4 列/均分 |
| 注意力检测 | 单选 + 正确答案 | `responses.value` | 作答 + 对错 |
| 反馈来源识别 | 单选 | `responses.value` | 作答 + 对错 |
| 作答时长/努力 | 时间戳 | `presented_at`/`answered_at`/`elapsed_ms` | 耗时列 |
| 流失 | 会话状态/活动时间 | `status`/`active_at` | 状态 |

这张表叫**追溯矩阵（traceability matrix）**。它保证：研究设计里的每个变量，都能在数据库和导出里找到落点；反过来，每个字段都能解释"为什么存在"。

> 【方法】做数据型产品，先画追溯矩阵，再建表。否则很容易"功能都做了，数据不能用"。

### 5.8 边界条件清单

开发前把这张清单过一遍，能省掉大量返工：

- [ ] 刷新页面：消息重播吗？倒计时重置吗？已答题还在吗？
- [ ] 关标签页再开：恢复还是新开？恢复窗口多久？
- [ ] 换设备/清缓存：旧会话怎么办？编号会重复吗？
- [ ] 同一台电脑做多个被试：怎么释放设备？
- [ ] 重复提交/迟到请求：会不会记到下一题？
- [ ] 提前提交：服务端拒绝后，前端怎么继续倒计时？
- [ ] 到点未作答：停在题上还是自动跳过？现场怎么兜底？
- [ ] 网络抖动：提交失败会重试吗？文本会丢吗？
- [ ] 管理员改题：进行中的会话受影响吗？
- [ ] 两组内容：除了操纵，还有别的差异吗？怎么自动校验？
- [ ] 清屏后刷新：之前的内容会回来吗？
- [ ] 标准答案：会被下发到前端吗？
- [ ] 导出：缺失值、多选、排序、题组怎么表示？
- [ ] 数据备份：WAL 文件一起备了吗？
- [ ] 时区/夏令时：时间戳用 UTC 还是本地？导出怎么显示？
- [ ] 并发：同一问卷几百人同时提交，编号会重复吗？

## 6. 可复用的需求分析方法（下次照这个做）

### 第一步：把原始材料改写成时间线

不要按文档章节，按"被试经历"写：

```text
时刻 T0：看到什么 → 能做什么 → 系统记什么
时刻 T1：……
```

### 第二步：给每个时刻标四件事

| 标记 | 问题 |
|---|---|
| 输入 | 被试/研究者要提供什么？格式、必填、校验？ |
| 输出 | 系统要显示/发送什么？内容从哪来？ |
| 时间 | 什么时候出现？能停留多久？到点怎么办？ |
| 数据 | 要记什么？给谁看？怎么导出？ |

### 第三步：抽实体与状态

- 名词 → 实体；
- 动词 → 状态迁移；
- 形容词/规则 → 校验与参数。

画出"一个实例从创建到结束"的状态图。状态图里每个箭头都要能对应一个 API 或一次提交。

### 第四步：写 FR + 验收口径

模板：

```text
FR-XX：<动词 + 对象>
优先级：P0/P1/P2
前置条件：……
主流程：1) … 2) … 3) …
异常：……
验收：Given … When … Then …
数据：落库字段 / 导出列
```

### 第五步：找隐藏需求（七类）

1. 时间（基准、时区、超时、倒计时）
2. 中断（刷新、断网、锁屏、换设备）
3. 异常（重复提交、空答案、非法值、并发）
4. 权限（谁能看、谁能改、数据隔离）
5. 审计（时间戳、重试、状态、操作记录）
6. 变更（模板改了、内容改了、版本怎么隔离）
7. 交付（目标环境、安装、备份、排障）

### 第六步：记录决策（ADR）

每条有争议的需求，写四行：

```text
背景：……
选项：A / B / C
决定：选 B
代价：……；什么时候重新评估：……
```

### 第七步：画追溯矩阵

研究变量 → 题目 → 落库字段 → 导出列。任何一列空着，都是风险。

### 第八步：先写验收用例，再写代码

至少覆盖：

- 正常走完一份问卷；
- 提前提交被拒；
- 刷新续做；
- 重复提交不串题；
- 两组内容差异正确；
- 导出列齐全。

## 7. 本项目的经验教训

1. **"一切皆题目"不是炫技，是被内容变更逼出来的。** 如果实验流程永远不变，硬编码更快；但研究材料会改十几版，统一模型省下的返工远超前期抽象成本。
2. **需求文档里的"30 秒"往往不是最终需求。** 它可能被"思考面板"替代；重要的是把时间做成参数，而不是写死。
3. **数据口径要提前定。** "编号"到底是谁的编号，这个问题在开发后期才发现，会牵动导出、界面、自检。
4. **把"不做"写下来。** 超时未作答不做自动跳过、切屏只提醒不记录、题卡不改气泡——这些都是明确的边界，不是遗漏。
5. **内容约束要用脚本守住。** 两组只差两处、反馈正文不能出现干扰选项、题数固定——这些靠人眼审不住，必须自动化。
6. **实验系统的验收标准不是"页面好看"，而是"数据可信"。** 每个时间戳、每个选项标签、每个状态，都要能解释。

## 8. 练习（建议动手）

### 练习 1：换一个研究设计

假设你要做一个 2×2 实验：反馈来源（AI/人类）× 反馈效价（正/负），因变量是任务投入度。

请产出：

- 变量表（自变量、因变量、操纵检验、控制变量）；
- 被试时间线；
- 至少 12 条 FR（含验收口径）；
- 实体与状态图；
- 追溯矩阵（变量 → 题目 → 字段 → 导出列）。

### 练习 2：找隐藏需求

针对"被试在手机上做 20 分钟实验"这个场景，列出至少 10 条隐藏需求，并按"时间/中断/异常/权限/审计/变更/交付"分类。

### 练习 3：做一次决策记录

从你的项目里挑一个"当时纠结过的选择"，按 ADR 四行写下来。重点写"代价"和"什么时候重新评估"。

### 练习 4：读本项目代码验证

- 打开 `db.js`，找到 `ITEM_TYPES`、`QUESTION_TYPES`、`ITEM_LIMITS`，解释三者区别；
- 打开 `server.js`，找到 `computeAction`、`applyStep`，对照 5.5/5.6 的伪代码；
- 打开 `scripts/consistency-check.js`，看它如何校验两组差异。
