# 02 · 技术选型

> 目标：学会在"约束"下做技术选型，而不是在"流行度"里做选择。看完你能解释本项目的每一层为什么这么选，也能为下一个项目独立写出选型决策记录。
>
> 先记住一句话：**技术选型不是选最强的，是选"在你的约束下，总成本最低、失败风险最小"的。**

---

## 1. 先把约束钉死

选型之前，把项目约束写成一张表。约束分两类：

- **硬约束**：违反就不能交付；
- **软约束**：违反会难受，但能妥协。

本项目的约束：

| 类型 | 约束 | 为什么是硬/软约束 |
|---|---|---|
| 硬 | 实验现场可能没有外网 | 没有网络就开不了实验；必须能局域网运行 |
| 硬 | 目标电脑可能没装 Node/数据库 | 实验助理不会配环境；必须双击即用 |
| 硬 | 被试用自己的手机 | 必须有移动端网页；不能要求装 App |
| 硬 | 计时必须可信 | 前端计时可被绕过；必须服务端权威 |
| 硬 | 两组材料只能差操纵 | 否则实验无效；需要自动校验 |
| 硬 | 数据要能直接进统计 | 研究者不做数据清洗；导出必须规整 |
| 硬 | 伦理：知情同意/欺骗解释/匿名 | 涉及人的研究，不能省 |
| 硬 | 预实验有日期 | 开发时间有限；先保证能收数据 |
| 软 | 几百人同时在线 | 2 核 2G 服务器；当前规模可满足 |
| 软 | 一个人 + AI 维护 | 不能引入长期升级负担 |
| 软 | 内容会反复改 | 研究者要能自己改；不能每次找开发 |
| 软 | 界面要像聊天、自然 | 影响操纵与体验；但不是数据正确性的前提 |

> 【方法】把约束按"违反后果"排序，而不是按"实现难度"排序。**违反就实验失败的约束，优先级最高。**

### 1.1 从约束直接推导技术方向

| 约束 | 推导 |
|---|---|
| 现场可能无外网 | 不能依赖云服务、CDN、在线字体、第三方 API；所有资源本地化 |
| 目标电脑没环境 | 不能要求 `npm install`、不能依赖数据库服务；单文件/单进程优先 |
| 被试手机 | 响应式 Web；不能依赖桌面端能力；要考虑锁屏/切后台 |
| 计时可信 | 服务端记录时间戳并在提交时校验；前端只显示 |
| 数据直接可用 | 后端结构化落库；导出宽表；字段口径固定 |
| 一个人维护 | 依赖越少越好；构建链越短越好；文档与自检要强 |
| 内容反复改 | 内容与代码分离；管理端可编辑；有同步/校验脚本 |

**技术选型不是从"我想学 React"开始，是从这张推导表开始。**

## 2. 第一个大选择：现成平台、实验框架，还是自研？

### 2.1 候选

| 方案 | 代表 | 优势 | 劣势 |
|---|---|---|---|
| 通用问卷平台 | Qualtrics、问卷星、SurveyMonkey | 零开发、稳、导出成熟 | 计时/流程控制弱；难做"AI 思考面板/流式输出"；离线/内网受限；数据在第三方 |
| 实验框架 | jsPsych、oTree、Labvanced、Gorilla | 刺激呈现精确、实验范式成熟 | 需要写代码；管理端/手机聊天/数据导出要另做；离线分发仍要自己解决 |
| 自研 | 本项目 | 完全贴合流程；离线；数据主权；可深度定制 | 开发成本高；要自己保证质量与安全 |

### 2.2 用加权矩阵把直觉变成可讨论的数字

权重按本项目约束设定（示例，不是绝对真理）：

|  criterion | 权重 | 问卷平台 | 实验框架 | 自研 |
|---|---:|---:|---:|---:|
| 时间/流程控制精度 | 25% | 3 | 4 | 5 |
| 离线/内网可用 | 20% | 1 | 4 | 5 |
| 定制与数据主权 | 20% | 2 | 4 | 5 |
| 开发速度 | 15% | 5 | 3 | 2 |
| 运维成本 | 10% | 5 | 3 | 4 |
| 学习/维护成本 | 10% | 5 | 2 | 2 |
| **加权总分** | 100% | **3.10** | **3.55** | **4.15** |

> 分数是主观的，但**把权重和分数写出来**，讨论就从"我觉得"变成"如果离线权重降到 5%，结论会不会变？"
>
> 敏感性检查：如果把"开发速度"权重提到 40%，问卷平台会赢。结论依赖约束——这正是选型要写清楚约束的原因。

### 2.3 为什么最后自研

1. **流程不是标准问卷**：消息流、思考面板、流式输出、强制阅读、共用窗口、清屏、重做，通用平台表达不了。
2. **离线是硬约束**：预实验在教室/实验室，不能保证外网；便携包必须自带运行时。
3. **数据要能直接分析**：导出格式、题号口径、正确答案对错、两次作品分列，通用平台要大量后处理。
4. **"AI"是实验刺激**：不能接真实模型；需要固定文案 + 可控节奏，这反而是自研更容易。
5. **内容会反复改**：需要一个研究者能自己用的管理端，而不是每次改代码。

**但没有完全抛弃前人的经验**：

- 题目模型参考了 Qualtrics/LimeSurvey 的"题目类型 + 参数"；
- 实验流程参考了 jsPsych 的"trial 序列"；
- 管理端交互参考了问卷星/Notion 的"就地插入、大纲、预览"。

> 【方法】自研不等于从零发明。把成熟产品的**模型**借过来，把不适用的**实现**丢掉。

## 3. 第二个大选择：技术栈

### 3.1 总表

| 层 | 选择 | 核心理由 | 替代方案 | 什么时候该换 |
|---|---|---|---|---|
| 运行时 | Node.js ≥ 22.13 | 前后端同语言；内置 `node:sqlite`；可打包 `node.exe` | Python/Django、Go | 团队更熟 Python；需要更强计算/并发 |
| HTTP | `node:http` | 零依赖、路由少、完全可控 | Express、Fastify、Nest | 路由/中间件/团队规模上来 |
| 数据库 | SQLite（`node:sqlite`） | 嵌入式、零运维、单文件备份、WAL 足够 | PostgreSQL、MySQL | 多实例、写入更高、复杂分析 |
| 前端 | 原生 HTML/CSS/JS | 无构建、部署简单、离线友好 | React/Vue + Vite | UI 状态复杂、团队协作、组件复用 |
| 富文本 | `contenteditable` + 自写清洗 | 与 Node 共用同一份清洗逻辑 | TipTap、Quill | 需要协同编辑/复杂排版 |
| Excel | 手写 OOXML + `deflate` | 零依赖、列/样式完全可控 | `exceljs`、`xlsx` | 需要公式、透视表、超大文件 |
| 二维码 | vendor 的 `qrcode-generator` | MIT、离线、单文件 | npm `qrcode` | 需要复杂样式/Logo |
| 鉴权 | `scrypt` + HMAC token | Node 内置、无依赖、可做单设备 | JWT 库、Session 存储 | 需要 OAuth/SSO/多服务 |
| 测试 | 自写 HTTP 客户端 + CDP | 零依赖、能跑真实浏览器 | Playwright、Jest | 团队/CI 要求、用例规模变大 |
| 部署 | 单进程 + zip 包 | 离线、一键、无需容器 | Docker、systemd、PM2 | 云上多实例、需要滚动发布 |

下面逐层解释。

### 3.2 运行时：Node.js 22

**为什么是 Node：**

- 前端已经是 JS，服务端同语言，减少上下文切换；
- `node:sqlite` 内置，不需要编译原生模块（Windows 上 `better-sqlite3` 需要 build tools，现场机器很可能没有）；
- `node.exe` 可以随便携包分发，目标电脑不装 Node 也能跑；
- 单线程事件循环 + 异步 I/O 适合"大量短请求、少量计算"的问卷场景。

**为什么不是 Python：**

- Python + Flask/FastAPI 也很好，但需要额外运行时/虚拟环境；便携包更重；
- 前端仍是 JS，双语言对单人项目是额外负担；
- `sqlite3` 在 Windows 上同样要编译/轮子，分发不如内置模块稳。

**什么时候该换：**

- 需要做复杂统计/机器学习/NLP 评分 → Python 生态更强，可以把分析拆成离线脚本；
- 需要 CPU 密集型任务（视频、图像）→ Node 单线程不占优。

### 3.3 HTTP：`node:http` 而不是 Express

**本项目的路由规模**：约 40 个 API + 静态资源。手写 `if (pathname === ...)` 可控、可读、无需中间件。

**收益：**

- 零依赖：没有 `node_modules`，便携包更小，供应链风险更低；
- 完全控制：限流、安全头、body 大小、错误格式都能按需写；
- 调试直接：请求进来就是函数调用，没有中间件栈。

**代价：**

- 路由/参数解析/错误处理都要自己写；
- `server.js` 会变成大文件（当前约 2475 行）；
- 团队协作时，缺少 Express 的约定，容易风格分叉。

**什么时候该换：**

- 路由 > 100 或需要大量中间件（认证、CORS、上传、限流）→ Express/Fastify；
- 团队 > 2 人 → 需要约定与分层，`node:http` 的自由会变成负担。

> 【方法】"零依赖"不是道德优势，是**分发约束**下的选择。如果项目部署在云上、有 CI、有团队，Express 的工程化收益更大。

### 3.4 数据库：SQLite + WAL

**为什么 SQLite：**

- 嵌入式：没有独立数据库进程，不需要安装/配账号/开端口；
- 单文件：`data.db` 可直接备份/拷贝；对实验现场极其友好；
- 事务与 SQL：比 JSON 文件可靠，支持索引、聚合、约束；
- WAL 模式：读写并发更好，提交不需要每次 fsync（`synchronous=NORMAL`）。

**性能是否够：**

项目文档记录的本机实测（不是生产保证）：

- 单请求平均 ~2.3ms，p95 ~6ms；
- 300 个会话同时提交：310ms（约 968 QPS）到 758ms（约 396 QPS），取决于版本与测试方式；
- 一位被试全程约 27–31 次请求，读题/打字/倒计时期间零请求。

**关键不是 QPS，是请求模型**：逐题提交、无轮询、服务端一次校验，所以几百人在线只有约 15 请求/秒。

**什么时候该换 PostgreSQL：**

- 需要多实例/水平扩展（SQLite 是单机单写者）；
- 写入量持续很高（每秒数百次以上写）；
- 需要复杂分析、全文检索、JSONB 查询；
- 需要跨机器高可用。

**迁移成本**：数据层集中在 `db.js`，SQL 不算多；但 `items_json`、时间戳、导出逻辑要逐条验证。不要因为"听说 Postgres 更好"就提前换。

> 【方法】数据库选型看"部署形态"和"写入模型"，不要只看 benchmark。单机、低运维、短请求，SQLite 往往被低估。

### 3.5 前端：原生 JS，无构建

**为什么不用 React/Vue：**

- 没有构建链：改完刷新即可，部署就是把文件拷过去；
- 离线友好：不需要 CDN、不需要 `node_modules`；
- 页面状态相对集中：被试端是"消息流 + 当前题卡"，管理端是"列表/编辑/预览"；
- 调试直接：DOM 就是状态，没有框架抽象层。

**代价（要诚实）：**

- `admin.js` 约 4358 行、`chat.js` 约 2162 行，靠函数与约定组织；
- 没有组件复用/类型检查，改一处要全局搜选择器；
- 复杂交互（拖拽排序、富文本、预览桥）手写成本高；
- 测试依赖 DOM 选择器，重构容易碎。

**什么时候该换：**

- 管理端继续变复杂（多人协作、权限、版本对比）→ React/Vue + Vite；
- 需要组件库/设计系统 → 框架生态更合适；
- 团队前端经验更强 → 不要为了"零依赖"让人写得不顺手。

**一个折中**：被试端保持原生（体积小、稳定、离线），管理端单独上框架。本项目没做，是因为当时管理端已成型，重写风险大于收益。

### 3.6 富文本：自写清洗，浏览器与 Node 共用

`public/assets/richtext.js` 同时被浏览器和管理端/`db.js` 引用。它负责：

- 清洗粘贴自 Word 的 HTML（去掉条件注释、还原 `&nbsp;`、保留编号）；
- 统一字号/加粗；
- 生成被试端可见的安全 HTML。

**为什么重要**：如果只在浏览器清洗，服务端仍可能收到脏 HTML；如果只在服务端清洗，编辑器预览与最终呈现会不一致。**同一份实现两边共用**，是这个小项目里很聪明的一处设计。

**代价**：自写清洗器很难覆盖所有 XSS 向量；需要 CSP、白名单、测试。若富文本是核心功能，应该用成熟库（TipTap/DOMPurify）。

### 3.7 Excel：手写 OOXML

`xlsx.js` 约 295 行，手写：

- ZIP 容器（`deflate`）；
- `[Content_Types].xml`、`workbook.xml`、`sheetN.xml`、`styles.xml`；
- 共享字符串/内联字符串；
- 列宽、加粗、居中、换行、数字格式。

**为什么：**

- 零依赖；导出格式完全可控（汇总表 Times New Roman 11、表头加粗居中换行）；
- 不需要在目标机器装 Office/库；
- 文件小、生成快。

**代价：**

- 只支持需要的子集；公式、图表、透视表、条件格式要自己加；
- OOXML 细节多，Excel/WPS 兼容性要实测；
- 维护成本高，出问题难搜。

**什么时候该换**：导出需求变复杂（多 sheet 样式、公式、图片、十万行）→ `exceljs`。

### 3.8 鉴权：scrypt + HMAC token

- 密码：`crypto.scrypt` + 随机盐，存 `pass_hash`/`salt`；
- Token：payload（uid、username、epoch、exp）+ HMAC-SHA256 签名，Base64URL；
- 单设备：`users.token_epoch`，登录/登出/改密时 +1，旧 token 的 `v` 对不上即失效；
- 管理 API：`Authorization: Bearer <token>`；
- 限流：登录按 IP/账号、注册按 IP、被试建会话按 IP/全局。

**为什么不用 JWT 库**：需求简单，HMAC 签名 + 过期 + epoch 足够；少一个依赖。**不是**因为"JWT 不安全"。

**注意**：这是"自用管理端"级别的鉴权，不是面向公网多租户的完整方案。若要开放注册/多角色/审计，应该用成熟方案（OIDC、Passport、Keycloak）。

### 3.9 测试：自写 HTTP + CDP

**为什么不用 Jest/Playwright：**

- 零依赖、离线可跑；
- 需要"直连数据库改时间戳"来跳过门控（时间旅行），通用框架反而绕；
- 需要跑真实浏览器截图与 DOM 断言，CDP 足够。

**做了什么：**

- `scripts/check-platform.js`：平台行为自检（题型、门控、恢复、导出），自带夹具，不依赖实验内容；
- `scripts/consistency-check.js`：当前内容配置自检（题数、量表、两组差异、反馈正文）；
- `scripts/capture-shots.js`：无头浏览器全流程截图 + 断言；
- `scripts/load-probe.js`：并发探针；
- `scripts/simulate-subjects.js`：走真实接口灌模拟数据；
- `scripts/lib/`：HTTP、会话驱动、直连数据库、xlsx 读取。

**关键经验**：把"等待 40 秒"改成"直接改数据库时间戳"，自检从 6 分 47 秒降到 0.7 秒，而且用的是真实门控值。**可测试性是架构属性**：时间戳存在数据库里，才能被测试快进。

**什么时候该换**：团队/CI 需要标准报告、并行、重试、可视化 → Playwright + Vitest/Jest；但保留"时间旅行"工具。

### 3.10 部署：单进程 + zip

**两种交付：**

| 交付物 | 内容 | 场景 |
|---|---|---|
| 预实验便携包 | 内置 `node.exe` + 运行文件 + 数据库快照（清空被试数据） | 实验室/教室，双击启动，手机扫码 |
| 上线包 | 仅代码，不含 `node.exe`/`data.db` | 公网服务器覆盖更新 |

**为什么不用 Docker：**

- 目标机器是 Windows Server/笔记本，Docker 不一定可用；
- 单进程 + 文件覆盖更符合现场运维能力；
- 便携包可以做到"双击即用"，容器做不到零学习成本。

**什么时候该换**：云上多实例、需要滚动发布/健康检查/自动扩缩 → Docker + 编排；但实验现场仍然可以保留便携包。

## 4. 一个特殊选型：不接真实 LLM

这看起来是产品决策，其实是技术选型。

| 选项 | 优点 | 缺点 | 本项目 |
|---|---|---|---|
| 真实 LLM 生成反馈 | 自然、个性化 | 不可复现、延迟/成本/隐私、内容不可控、可能违规 | 不用 |
| 预写反馈 + 模拟思考/流式 | 完全标准化、离线、可复现、零成本 | 不"智能"，内容固定 | **采用** |
| 预写反馈 + 真实 LLM 只做改写 | 兼顾自然与可控 | 仍有方差；需要审核 | 未采用 |

**为什么实验必须固定反馈**：研究要比较"负面反馈"的影响，如果每个人收到的内容不同，就无法归因。**在这里，"不智能"是特性，不是缺陷。**

**如果将来要接 LLM**，至少要加：

- 固定 prompt + 固定模型版本 + 温度 0；
- 生成结果缓存/审核/版本号；
- 超时与降级到固定文案；
- 不把被试作品/个人信息发给第三方；
- 记录模型版本，保证可复现。

## 5. 技术选型方法（下次照这个做）

### 第一步：写约束表

按"硬/软"和"违反后果"排序。不要先列技术。

### 第二步：列候选（2–4 个）

每个候选写：它擅长什么、不擅长什么、在什么条件下会赢。

### 第三步：设权重，做矩阵

权重来自约束，不来自喜好。做完做一次**敏感性检查**：把最重要的权重上下调 10–20%，结论会变吗？如果会变，说明你的偏好不稳，需要更多证据。

### 第四步：做 spike（技术验证）

只验证"最可能推翻方案"的假设，不做完整原型。本项目的关键 spike：

- `node:sqlite` 在目标 Node 版本可用吗？WAL 并发写入表现如何？
- 300 个并发提交会不会 `SQLITE_BUSY`？
- CDP 能不能驱动无头浏览器完成全流程？
- 手写 xlsx 能不能被 Excel/WPS 正常打开？
- 便携包在没装 Node 的 Windows 上能不能双击启动？

> 【方法】spike 的产出不是代码，是**结论 + 证据**（命令、数据、截图）。验证完就删掉原型，别让它变成半成品。

### 第五步：写 ADR

模板：

```markdown
# ADR-003：使用 SQLite 作为主数据库

## 背景
单机实验平台，几百并发，零运维，数据要能整库备份。

## 选项
A. SQLite（node:sqlite）
B. PostgreSQL
C. JSON 文件

## 决定
选 A。

## 理由
- 单文件、零安装、WAL 足够当前并发；
- 数据层集中在 db.js，未来换库可控；
- 便携包可直接带走数据库快照。

## 代价
- 单写者，不能多实例；
- 复杂分析能力弱；
- 迁移需要重写部分 SQL。

## 重新评估的触发条件
- 需要多实例/水平扩展；
- 持续写入 > 每秒数百；
- 需要复杂分析/全文检索。
```

### 第六步：设"重新评估触发器"

选型不是一劳永逸。给每个选择写一句："出现什么信号时，我们要重新考虑？"

本项目的触发器示例：

- SQLite → Postgres：多实例、持续高写入、复杂分析；
- 原生前端 → 框架：管理端状态复杂度继续上升、团队多人；
- 手写 xlsx → 库：导出需要公式/图表/十万行；
- 自写测试 → Playwright：需要 CI 报告/并行/团队协作；
- 单进程 → 容器：云上多实例、滚动发布；
- 固定反馈 → LLM：研究问题本身需要个性化反馈（且能接受方差）。

## 6. 本项目的技术债与演进建议

| 技术债 | 表现 | 风险 | 建议 |
|---|---|---|---|
| `server.js` 单文件 | 2475 行，路由/状态机/鉴权/导出混在一起 | 改动牵一发动全身 | 拆 `routes/`、`services/`、`state-machine.js` |
| `admin.js` 单文件 | 4358 行 | 难维护、难测试 | 管理端引入框架或至少拆模块 |
| item JSON 无 schema | 字段靠 `normalizeItem` 兜底 | 脏数据、编辑器漏字段 | 引入 JSON Schema/zod 校验 |
| 手写迁移 | `ensureColumn` + 删旧表 | 生产升级有风险 | 引入版本化 migration |
| 手写 xlsx | 只支持子集 | 复杂导出受限 | 需要时换 `exceljs` |
| 自写清洗器 | XSS 覆盖有限 | 富文本安全 | 引入 DOMPurify 或成熟编辑器 |
| CSP 含 `unsafe-inline/eval` | 为截图工具放宽 | 安全弱化 | 截图改 CDP 求值后收紧 |
| 无正式 CI | 自检靠本地 | 回归风险 | GitHub Actions 跑 `npm run check` |
| 单机 SQLite | 无法水平扩展 | 规模上限 | 到量再换 Postgres |
| 内容双份（种子/线上） | 改种子后要同步脚本 | 配置漂移 | 以管理端为唯一源，种子只用于初始化 |

> 【方法】技术债不可怕，可怕的是不知道它的**触发条件**。把"什么时候必须还"写下来。

---

## 7. 面试/复盘时怎么讲选型

不要背"用了 Node + SQLite + 原生 JS"，要讲**约束—选择—代价**：

> "这个项目的硬约束是实验现场可能没有外网、目标电脑不能装环境、计时必须可信。所以我选了 Node 单进程 + 内置 SQLite + 无构建前端，打包成内置 node.exe 的便携包。代价是管理端代码偏大、SQLite 不能多实例；如果将来上云多实例，我会把数据层换 Postgres，管理端拆成 React。"

这段话包含了：约束、选择、代价、演进。比列技术栈有说服力得多。

## 8. 练习

1. 给你的项目写一张约束表（硬/软各至少 5 条），并推导技术方向。
2. 用加权矩阵比较 3 个方案，做一次敏感性检查。
3. 选一个你拿不准的技术点，设计一个 30 分钟的 spike，写出"验证什么、怎么验证、通过标准"。
4. 为你的数据库选择写一份 ADR，必须包含"重新评估的触发条件"。
5. 找出你项目里最可能过时的技术选择，写出迁移路径与成本。
